# Native EspoCRM 9.1.7 view-family audit

Source: official tag `9.1.7` (`4baab4dff4342ed1b194015407c8bc74b4cc9a7d`). Counts include every `.js` view file under the family directory, recursively. `core` is `client/src/views`; `crm` is `client/modules/crm/src/views`. The 83 family folders are listed individually; the `(root)` bucket contains view files directly under `views/` and is not a family folder.

No row is marked complete: this audit exists to keep the 100% target explicit. “Partial” means a replacement component exists, but every native view behavior and action has not been proven. “Generic CRUD only” does not count as parity for custom native behavior.

## Known cross-family gaps

- Native public entrypoints (`LeadCaptureForm`, event confirmation, unsubscribe, campaign tracking, password-change links) render on the EspoCRM site origin. React replacements now cover Lead Capture, opt-in, event RSVP, unsubscribe, tracking pixels and password-change requests; the client is still served separately on port 5173, so native links route into it only when production proxying serves the replacement on the configured CRM origin.
- Admin and CRM records that use generic CRUD have not been counted as complete where native controllers add custom behavior.
- Field widgets, modal flows, layout variants, and extension-provided views need an exhaustive behavior inventory, not a folder-name match.
- `packages/ViaCRM-Frontend-2.0.1.zip` now packages the React production build under `client/custom/viacrm/` together with the API bridge for installation and upgrades through Administration → Extensions. Serving it under the native root URL and routing EspoCRM-generated public entrypoint links through the replacement still requires same-origin web-server/reverse-proxy configuration; the package documents that deployment step and does not overwrite core `index.php` or native client files.
